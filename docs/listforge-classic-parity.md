# Paridade funcional — ListForge Integrado (modo Clássico) vs. ListForge Standalone

Referência usada: **C:\Projetos\ListForge**, branch `main`, commit `f429381` (2026-10-22,
"feat: export JSON with piece gender suffix and SISBolt-compatible fields"),
`ListForge.csproj` → `<Version>2.1.44</Version>`. **Não** existe `F:\Projetos\ListForge` nesta
máquina — esse caminho, citado em pedidos anteriores, não corresponde a nenhum checkout real
aqui; o único repositório do standalone encontrado é o acima, que já era usado como referência
de `ListForge.Core` por este repositório.

Esta tabela substitui qualquer caracterização anterior e mais superficial do ListForge
Integrado em `README.md`/`ROADMAP.md`/`docs/ARCHITECTURE.md` — leia o código do standalone
listado na coluna "Referência no código" como fonte de verdade, não a documentação anterior
deste repositório.

**Como ler "Estado no integrado"**: *Completo* exige lógica E comportamento de erro
equivalentes, não só um botão com o mesmo nome. *Parcial* = existe, mas com lacuna real de
opção/robustez. *Ausente* = não existe no integrado hoje. *Exclusivo do standalone* = não deve
existir no integrado por decisão de arquitetura já tomada (`AGENTS.md`: cada distribuição tem
identidade própria; o ListForge standalone "continua existindo permanentemente, independente do
CorelDRAW/PX").

**Achado estrutural importante**: o namespace `ListForge.Core` é usado tanto pelo projeto
compartilhado `ListForge.Core.csproj` (`C:\Projetos\ListForge\ListForge.Core\`, referenciado por
este repositório) quanto pela pasta `Core\` do projeto do standalone
(`C:\Projetos\ListForge\Core\`, **não compartilhada** — compila só dentro de `ListForge.csproj`).
Mesmo namespace, dois lugares físicos diferentes. Uma classe como `TextSearchHelper` parecer
"já no núcleo" pelo nome completo (`ListForge.Core.TextSearchHelper`) não significa que o host do
PX já consiga chamá-la — é preciso confirmar em qual dos dois projetos o arquivo físico está.
